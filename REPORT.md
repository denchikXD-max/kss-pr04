### 2.4. Проєктні рішення та додаткове завдання (на відмінно)

- **Дія зміни стану:** повернення книги оформлено як POST на `/loans/{loanId}/return` з розширенням `x-kss-action: true` (успіх: 200, якщо стан суперечить — 409 Conflict).
- **Ідемпотентність:** GET, DELETE ідемпотентні за специфікацією HTTP; PATCH захищено оптимістичним блокуванням за заголовком `If-Match`. POST неідемпотентний.
- **Версіонування:** в URL `/api/v1`.
- **Формат помилок:** RFC 9457 `application/problem+json` (`ProblemDetails`, для валідації 422 — `ValidationProblem`).
- **Адреса створеного ресурсу:** заголовок `Location` у відповіді `201 Created`.
- **Умовні запити:** операція `GET /books/{bookId}` повертає `ETag` (підтримує `304 Not Modified`); `PATCH /books/{bookId}` приймає `If-Match` і при невідповідності повертає `412 Precondition Failed`.
- **План еволюції та переходу на `/api/v2`:** використання стандартизованих заголовків `Deprecation` і `Sunset` у відповідях застарілої версії v1 із наданням перехідного періоду для оновлення клієнтів.

## 3. Взаємне рецензування (Завдання 5)

Під час взаємного рецензування проєкту `DESIGN.md` було зафіксовано такі зауваження та виправлення:
1. **Зауваження:** У попередньому варіанті для операції повернення книги використовувався шлях із дієсловом `POST /loans/{loanId}/return-book`.  
   *Виправлення:* Приведено до вимог REST: використано підресурс стану `POST /loans/{loanId}/return`.
2. **Зауваження:** Для операції `DELETE /books/{bookId}` повертався код `200 OK` замість стандартизованого для видалення коду.  
   *Виправлення:* Встановлено код `204 No Content` без тіла відповіді.
3. **Зауваження:** У маршруті повернення книги не було передбачено код стану для ситуації, коли книга вже повернута раніше.  
   *Виправлення:* Додано код `409 Conflict` для захисту від повторної зміни стану вже закритої видачі.

## 6. Відповіді на контрольні запитання

### 1. Що таке ресурс і представлення ресурсу? Чому шляхи містять іменники, а не дієслова?
- **Ресурс** — це фундаментальна абстракція в архітектурі REST, будь-яка іменована концептуальна сутність предметної області, до якої можна звернутися за постійним уніфікованим ідентифікатором (URI), наприклад, книга, читач або видача.
- **Представлення ресурсу (representation)** — це поточний або запитуваний стан ресурсу в конкретному форматі передачі даних (найчастіше JSON або XML), що супроводжується метаданими (HTTP-заголовками, такими як `Content-Type`).
- **Чому іменники, а не дієслова:** В архітектурному стилі REST дію над ресурсом визначає стандартний метод протоколу HTTP (`GET` — читати, `POST` — створити, `PATCH` — оновити, `DELETE` — видалити). Якщо поміщати дієслова в URI (наприклад `/getBooks`, `/deleteBook`), це перетворює REST на RPC (Remote Procedure Call), порушує принцип уніфікованого інтерфейсу та унеможливлює стандартне кешування й оптимізацію мережевих посередників.

### 2. Як моделювати дію, що не вкладається в CRUD (зміна стану)? Наведіть приклад зі свого варіанта.
Дії зі складною бізнес-логікою або переходом між станами життєвого циклу моделюють через підресурс-дію методом `POST` над конкретним ресурсом: `POST /колекція/{id}/дія`. У нашому варіанті «Бібліотека коледжу» повернення книги читачем змодельовано як `POST /loans/{loanId}/return`. Така операція перевіряє поточний стан (чи позика активна), фіксує дату повернення, збільшує лічильник доступних примірників книги та повертає код `200 OK` з оновленим об'єктом. Якщо книга вже повернена раніше, повертається код `409 Conflict`.

### 3. Які методи HTTP безпечні та ідемпотентні? Навіщо це знати, проєктуючи API?
- **Безпечні методи (safe):** `GET`, `HEAD`, `OPTIONS`. Їх виклик не змінює стан сервера (операції лише для читання). Мережеві агенти й пошукові роботи можуть без ризику виконувати їх автоматично.
- **Ідемпотентні методи (idempotent):** `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`. Повторення одного й того самого запиту N разів призводить до точно такого самого стану системи, як і один виклик.
- **Неідемпотентні методи:** `POST`, `PATCH` (в загальному випадку без умовних заголовків).
- **Навіщо це знати:** Це критично для проектування надійності в умовах ненадійної мережі. Якщо під час виклику ідемпотентного методу трапився розрив зв'язку чи тайм-аут, клієнт або бібліотека повторних спроб (retry logic) може безпечно повторити запит без загрози створення дублікатів чи спотворення даних.

### 4. Чим відрізняються коди 400, 409 і 422? 401 і 403? Коли повертати 204?
- **400 vs 409 vs 422:**
  - `400 Bad Request` — запит синтаксично некоректний (зламаний JSON, невірний тип HTTP-запиту, синтаксична помилка в заголовках чи query-параметрах).
  - `422 Unprocessable Entity` — синтаксис JSON коректний, але семантика даних не проходить валідацію бізнес-правил (відсутнє обов'язкове поле, неприпустимий формат email, від'ємне число тощо).
  - `409 Conflict` — дані коректні й валідні самі по собі, але запит суперечить поточному стану ресурсів на сервері (спроба повернути вже повернену книгу, видати примірник, який уже знаходиться в іншого читача, або видалити книгу, за якою є неповернені видачі).
- **401 vs 403:**
  - `401 Unauthorized` — автентифікація обов'язкова, але користувача не впізнано (токен відсутній, прострочений або недійсний). Заголовок відповіді вказує спосіб автентифікації.
  - `403 Forbidden` — користувача успішно автентифіковано, але його права/роль не дозволяють виконати цю операцію (наприклад, читач намагається зареєструвати нову книгу або списати примірник).
- **Коли повертати 204 No Content:** коли сервер успішно виконав операцію, але клієнту не потрібно повертати жодного тіла відповіді. Класичний випадок — успішне видалення ресурсу (`DELETE`).

### 5. Порівняйте пагінацію зі зміщенням (page/pageSize) і курсорну. Коли доцільна кожна?
- **Пагінація зі зміщенням (`page`, `pageSize` / `offset`, `limit`):**
  - *Принцип:* пропускає `(page - 1) * pageSize` записів у базі даних (`OFFSET`).
  - *Переваги:* простота реалізації, легкий перехід на довільну сторінку (наприклад, перехід одразу на 5-ту сторінку в UI), відображення загальної кількості сторінок.
  - *Недоліки:* деградація продуктивності на великих базах даних ($O(N)$ для `OFFSET`), проблема зсуву результатів (дублікати або пропуск елементів, якщо паралельно вставляються нові записи).
- **Курсорна пагінація (`cursor`, `limit`):**
  - *Принцип:* клієнту повертається непрозорий покажчик на останній елемент сторінки (наприклад `id` або `timestamp`), і наступний запит вибирає записи `WHERE id > cursor LIMIT N`.
  - *Переваги:* стабільна продуктивність $O(1)$ завдяки індексам, відсутність дублікатів при додаванні нових записів.
  - *Недоліки:* неможливість перейти одразу на довільну сторінку (лише вперед/назад).
- *Висновок:* зміщення підходить для звичайних адмін-панелей і невеликих каталогів (як у бібліотеці коледжу), курсорна — для великих нескінченних стрічок новин, подій та високонавантажених логів.

### 6. Які способи версіонування API ви знаєте? Які зміни вимагають нової версії?
- **Способи версіонування:**
  1. *У шляху URI (URI Path):* `/api/v1/books` — найбільш наочний, підтримується кешуванням і проксі.
  2. *У рядку запиту (Query Parameter):* `/api/books?version=1`.
  3. *Через власний заголовок:* `X-API-Version: 1`.
  4. *Через узгодження вмісту (Content Negotiation / Header Accept):* `Accept: application/vnd.college.v1+json`.
- **Зміни, що вимагають нової мажорної версії (несумісні/breaking):**
  - Видалення або перейменування існуючого ресурсу чи поля в JSON;
  - Зміна типу даних поля;
  - Додавання нового обов'язкового поля в запит створення/оновлення;
  - Зміна семантики існуючого коду відповіді або структури повернення помилок.

### 7. З яких розділів складається специфікація OpenAPI? Навіщо components і $ref?
- **Основні розділи:** `openapi` (версія стандарту), `info` (метадані, назва, версія API, автор), `servers` (адреси хостів), `tags` (групування маршрутів), `paths` (ендпоінти, методи HTTP, параметри та відповіді), `components` (перевикористовувані схеми, параметри, заголовки, відповіді), `security` (глобальні вимоги безпеки).
- **Навіщо `components` і `$ref`:** Вони забезпечують дотримання принципу DRY (*Don't Repeat Yourself*). Замість дублювання схеми `ProblemDetails` чи опису моделі `Book` у десятках операцій, їх описують один раз у `components` і посилаються через вказівник JSON Pointer `$ref: "#/components/schemas/Book"`. Це зменшує розмір специфікації, полегшує підтримку та запобігає розбіжностям у типах.

### 8. Що дає підхід «спершу проєкт» (design-first) порівняно з генерацією специфікації з коду?
- **Паралельна розробка:** Frontend і backend команди погоджують контракт до написання коду. Фронтенд-розробники можуть одразу генерувати клієнти й працювати з mock-сервером (Prism), не чекаючи бекенду.
- **Економія часу й коштів:** Виправлення помилки в маршруті чи назві поля на етапі специфікації займає хвилини, тоді як переробка після написання бази даних, моделей і бізнес-логіки вимагає значних рефакторингів.
- **Чистота REST-архітектури:** Код не диктує випадкові деталі внутрішньої реалізації (наприклад, назви таблиць чи ORM-структур) назовні; публічний API проектується з точки зору зручності споживача.
- **Автоматизація:** Специфікація стає єдиним джерелом правди (*single source of truth*) для документації, валідаторів, тестів контрактів та генераторів клієнтського SDK.

## 8. Висновки

Під час виконання практичної роботи № 4 було опановано підхід «спершу проєкт» (*design-first*) для проєктування повноцінного REST API інформаційної системи бібліотеки коледжу:
1. Виділено ключові ресурси (`books`, `copies`, `readers`, `loans`), визначено їхні зв'язки, серверні та клієнтські поля.
2. Побудовано узгоджену таблицю з 15 маршрутів, що охоплює CRUD-операції, вкладену колекцію примірників, підресурсну дію зміни стану повернення книги, обмеження за ролями та стандартизовані відповіді помилок за стандартом RFC 9457.

5. Проведено перевірку ключових сценаріїв взаємодії (успішне створення, валідація схеми з помилкою 422, відмова в доступі 401) на живому імітаційному сервері Prism.
6. Виконано додаткові завдання підвищеної складності: проєктування умовних запитів з оптимістичним блокуванням (`ETag`, `304`, `If-Match`, `412`) та стратегію плавної міграції версій за допомогою стандартних заголовків `Deprecation` і `Sunset`.
